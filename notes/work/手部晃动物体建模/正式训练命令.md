# SONIC HEFT-WPC 正式训练命令

本文用于在单台 8 GPU 服务器上启动 SONIC HEFT-WPC 正式训练，并解释每一条命令和每一个参数。

本文假设：

- SONIC 工程位于 `/root/xuxiangling/sonic`；
- Conda 安装在 `/root/miniconda3`；
- Conda 环境名为 `sonic_z`；
- 当前 Git 分支为 `feat/wpc-heavy-payload`；
- 服务器有 8 张可用 GPU，编号为 `0` 到 `7`；
- WPC 初始 checkpoint 为 `sonic_release/last_wpc.pt`；
- 正式 robot 动作数据位于 `/mnt/nfs/humanoid/sonic/robot_filtered`；
- 正式 SMPL 动作数据位于 `/mnt/nfs/humanoid/sonic/smpl_filtered`；
- 环境检查、WPC 单元测试、小规模冒烟训练和中等规模试跑均已通过。

如果服务器路径或 GPU 数量不同，必须修改对应参数，不能原样照搬。

## 1. 为什么建议使用 tmux

`tmux` 会在服务器上创建一个独立的终端会话。训练进程运行在这个服务器端会话中，而不是直接依附于当前 SSH 连接。

如果直接在普通 SSH 终端中启动训练：

```text
SSH 连接断开
    ↓
Shell 退出
    ↓
训练进程可能收到挂断信号并停止
```

如果在 tmux 中启动：

```text
SSH 连接断开
    ↓
tmux 会话仍留在服务器
    ↓
训练进程继续运行
    ↓
重新连接服务器后再次进入 tmux
```

因此，长时间正式训练强烈建议使用 tmux。

tmux 不能处理以下情况：

- 服务器重启或断电；
- 训练程序自身崩溃；
- CUDA OOM；
- 进程被管理员或 OOM Killer 杀死；
- 磁盘空间耗尽；
- 用户主动结束 tmux 会话。

tmux 只能解决“SSH 断线后保持进程运行”的问题，不是训练容错或 checkpoint 系统。

## 2. 检查 tmux

检查服务器是否安装了 tmux：

```bash
command -v tmux
```

如果输出类似：

```text
/usr/bin/tmux
```

说明已经安装。

如果没有输出，可以在 Ubuntu 上安装：

```bash
apt update
apt install -y tmux
```

`apt update` 更新系统软件包索引。

`apt install -y tmux` 安装 tmux，`-y` 表示自动确认安装。

## 3. 正式训练前检查

### 3.1 进入工程

```bash
cd /root/xuxiangling/sonic
```

`cd` 表示切换目录。后续命令必须在 SONIC 工程根目录执行。

确认当前目录：

```bash
pwd
```

预期输出：

```text
/root/xuxiangling/sonic
```

### 3.2 检查 Git 分支

```bash
git branch --show-current
```

预期输出：

```text
feat/wpc-heavy-payload
```

WPC worker 脚本会强制检查这个分支。如果不是该分支，脚本会退出。

### 3.3 检查初始 checkpoint

```bash
test -s /root/xuxiangling/sonic/sonic_release/last_wpc.pt \
  && echo "[OK] last_wpc.pt" \
  || echo "[FAIL] last_wpc.pt 不存在或为空"
```

`test -s` 检查文件是否存在，并且文件大小是否大于零。

`&&` 表示前面的检查成功时执行后面的 `[OK]`。

`||` 表示前面的检查失败时输出 `[FAIL]`。

### 3.4 检查正式动作数据

```bash
test -d /mnt/nfs/humanoid/sonic/robot_filtered \
  && echo "[OK] robot 动作数据" \
  || echo "[FAIL] robot 动作数据不存在"

test -d /mnt/nfs/humanoid/sonic/smpl_filtered \
  && echo "[OK] SMPL 动作数据" \
  || echo "[FAIL] SMPL 动作数据不存在"
```

`test -d` 检查指定目录是否存在。

这两个目录缺少任何一个，都不要启动正式训练。

### 3.5 检查 GPU

```bash
nvidia-smi -L
```

该命令列出服务器可见的 NVIDIA GPU。正式命令使用 GPU `0` 到 `7`，所以应确认至少有 8 张 GPU。

再检查当前 GPU 是否被其他任务占用：

```bash
nvidia-smi
```

重点查看：

- GPU 0 到 7 是否存在；
- 每张 GPU 的显存占用；
- `Processes` 区域是否有其他用户的训练进程；
- 是否有足够显存运行本任务。

即使大家都使用 root，也不要直接覆盖正在使用的 GPU。

### 3.6 检查通信端口

本文使用本机端口 `29633`：

```bash
ss -ltnp | grep ':29633'
```

如果没有输出，通常表示端口没有被监听，可以使用。

如果有输出，说明其他进程可能已经占用该端口。应把正式训练命令中的：

```text
MASTER_PORT=29633
```

改为其他空闲端口，例如 `29634`，并重新检查。

### 3.7 检查磁盘空间

```bash
df -h /root/xuxiangling/sonic
```

`df -h` 显示所在文件系统的总容量、已用空间和可用空间。

正式训练会生成多个 `.pt` checkpoint、日志和 Isaac Sim 缓存，应提前保留足够空间。

## 4. 创建 tmux 训练会话

创建名为 `sonic_wpc_train` 的会话：

```bash
tmux new -s sonic_wpc_train
```

参数含义：

- `tmux new`：创建新的 tmux 会话；
- `-s sonic_wpc_train`：将会话命名为 `sonic_wpc_train`。

执行后会进入一个新的终端界面。后面的正式训练命令要在这个 tmux 界面中执行。

如果提示会话已经存在，不要重复创建，可以使用：

```bash
tmux attach -t sonic_wpc_train
```

`attach` 表示进入已经存在的会话，`-t` 指定目标会话名称。

## 5. 单机 8 GPU 正式训练命令

在 tmux 会话中执行：

```bash
cd /root/xuxiangling/sonic

SONIC_REPO=/root/xuxiangling/sonic \
SONIC_CONDA_ENV=sonic_z \
CONDA_SH=/root/miniconda3/etc/profile.d/conda.sh \
NNODES=1 \
NODE_RANK=0 \
NPROC=8 \
RANK0_IP=127.0.0.1 \
MASTER_ADDR=127.0.0.1 \
MASTER_PORT=29633 \
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 \
NUM_ENVS=4096 \
NUM_STEPS_PER_ENV=24 \
EXP_VAR=sonic_wpc_server_001 \
CHECKPOINT=/root/xuxiangling/sonic/sonic_release/last_wpc.pt \
CHECKPOINT_ROOT=/root/xuxiangling/sonic/training_checkpoints \
MOTION_FILE=/mnt/nfs/humanoid/sonic/robot_filtered \
SMPL_MOTION_FILE=/mnt/nfs/humanoid/sonic/smpl_filtered \
USE_WANDB=False \
WANDB_MODE=disabled \
./sonic_launch/heft_wpc/run_sonic_wpc_rank0.sh \
++algo.config.num_learning_iterations=30000
```

每行末尾的 `\` 表示命令还没有结束，下一行仍属于同一条命令。

在参数赋值和训练脚本之间不要插入空行，也不要删除行尾的 `\`。

## 6. 正式训练参数逐项解释

### 6.1 `SONIC_REPO`

```bash
SONIC_REPO=/root/xuxiangling/sonic
```

指定 SONIC 工程根目录。

worker 会使用这个路径：

- 检查 `.git` 是否存在；
- 检查 Git 分支；
- 切换到工程根目录；
- 查找训练入口和配置文件。

### 6.2 `SONIC_CONDA_ENV`

```bash
SONIC_CONDA_ENV=sonic_z
```

指定训练使用的 Conda 环境名称。

启动脚本会在子进程中激活这个环境。训练结束后，外层终端仍可能显示 `(base)`，这是正常现象。

### 6.3 `CONDA_SH`

```bash
CONDA_SH=/root/miniconda3/etc/profile.d/conda.sh
```

指定 Conda 的 Shell 初始化脚本。

worker 会执行类似：

```bash
source /root/miniconda3/etc/profile.d/conda.sh
conda activate sonic_z
```

如果这个路径错误，脚本无法正确激活 `sonic_z`。

### 6.4 `NNODES`

```bash
NNODES=1
```

表示本次训练只使用一台服务器。

两台服务器联合训练时应设置为 `2`，但本文是单机训练，因此必须是 `1`。

### 6.5 `NODE_RANK`

```bash
NODE_RANK=0
```

表示当前服务器是第 0 号节点。

单机训练只有一个节点，所以它既是第一个节点，也是 rank 0。

`run_sonic_wpc_rank0.sh` 本身也会设置 `NODE_RANK=0`，这里显式写出是为了让配置更清楚。

### 6.6 `NPROC`

```bash
NPROC=8
```

表示当前服务器启动 8 个训练进程。

通常一个训练进程对应一张 GPU，因此：

```text
8 个进程 ↔ 8 张 GPU
```

`NPROC` 必须与实际准备使用的 GPU 数量一致。

### 6.7 `RANK0_IP`

```bash
RANK0_IP=127.0.0.1
```

指定 rank-0 节点地址。

`127.0.0.1` 表示当前服务器自己。因为这是单机训练，所有训练进程都在同一台机器，所以使用回环地址最合适。

多机训练时不能使用 `127.0.0.1`，必须改为 rank-0 服务器能被其他服务器访问的真实局域网 IP。

### 6.8 `MASTER_ADDR`

```bash
MASTER_ADDR=127.0.0.1
```

这是 `torchrun` 真正使用的主节点地址。

多个 GPU 训练进程通过这个地址集合、同步梯度和交换状态。

单机训练中，`RANK0_IP` 和 `MASTER_ADDR` 都设为 `127.0.0.1`。同时设置两者可以避免当前终端中残留的旧环境变量改变实际地址。

### 6.9 `MASTER_PORT`

```bash
MASTER_PORT=29633
```

指定多进程通信使用的本机端口。

完整通信地址是：

```text
127.0.0.1:29633
```

它只用于当前服务器内部的训练进程通信，不会连接互联网。

同一台服务器上的两个训练任务不能同时使用同一个 `MASTER_PORT`。

### 6.10 `CUDA_VISIBLE_DEVICES`

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7
```

允许本次任务看到物理 GPU 0 到 7。

如果只使用 4 张 GPU，应改为：

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3
```

并同时把 `NPROC` 改成 `4`。

### 6.11 `NUM_ENVS`

```bash
NUM_ENVS=4096
```

表示每个训练进程创建 4096 个 Isaac Lab 并行环境。

在 8 个训练进程下，理论并行环境总数是：

```text
4096 × 8 = 32768
```

每个环境中都有一台独立的仿真机器人。

这个参数会显著影响 GPU 显存。发生 CUDA OOM 时，可以依次降低为：

```text
2048
1024
512
```

降低 `NUM_ENVS` 会改变每轮训练采集的数据量，因此正式实验应记录实际使用值。

### 6.12 `NUM_STEPS_PER_ENV`

```bash
NUM_STEPS_PER_ENV=24
```

表示每次 PPO 更新前，每个仿真环境采集 24 个控制步骤。

在 8 个进程、每个进程 4096 个环境时，每轮大约采集：

```text
8 × 4096 × 24 = 786432
```

个环境步骤，然后进行 PPO 神经网络更新。

WPC curriculum 的默认配置也是按照 24 步设计的，因此正式训练保留这个值。

### 6.13 `EXP_VAR`

```bash
EXP_VAR=sonic_wpc_server_001
```

指定本次实验名称。

这个名称会用于 checkpoint 目录和 torchrun 日志目录。

如果重新开始一个不同实验，建议改名，例如：

```text
sonic_wpc_server_002
```

不要把不同配置的训练结果放进同一个实验目录。

### 6.14 `CHECKPOINT`

```bash
CHECKPOINT=/root/xuxiangling/sonic/sonic_release/last_wpc.pt
```

指定正式训练的初始模型。

`last_wpc.pt` 是在原始 SONIC release checkpoint 基础上，为 WPC critic 新增输入维度后生成的兼容 checkpoint。

训练不会覆盖这个输入文件。新的 checkpoint 会写入 `CHECKPOINT_ROOT/EXP_VAR`。

### 6.15 `CHECKPOINT_ROOT`

```bash
CHECKPOINT_ROOT=/root/xuxiangling/sonic/training_checkpoints
```

指定所有训练结果的根目录。

与 `EXP_VAR` 组合后的实际输出目录是：

```text
/root/xuxiangling/sonic/training_checkpoints/sonic_wpc_server_001
```

### 6.16 `MOTION_FILE`

```bash
MOTION_FILE=/mnt/nfs/humanoid/sonic/robot_filtered
```

指定正式 robot 参考动作数据目录。

正式训练不能再使用冒烟测试的少量 `sample_data`。

### 6.17 `SMPL_MOTION_FILE`

```bash
SMPL_MOTION_FILE=/mnt/nfs/humanoid/sonic/smpl_filtered
```

指定正式 SMPL 人体动作数据目录。

robot 和 SMPL 数据会共同为 SONIC 提供参考动作。

### 6.18 `USE_WANDB`

```bash
USE_WANDB=False
```

告诉 SONIC 训练代码不初始化 W&B。

### 6.19 `WANDB_MODE`

```bash
WANDB_MODE=disabled
```

告诉 W&B 库完全禁用联网和记录。

`USE_WANDB=False` 和 `WANDB_MODE=disabled` 同时设置，可以避免共享服务器因为缺少 W&B 登录信息而阻塞或报错。

如果以后需要使用 W&B，应单独配置账号，并把二者改成适当的在线配置。

### 6.20 WPC rank-0 启动脚本

```bash
./sonic_launch/heft_wpc/run_sonic_wpc_rank0.sh
```

该脚本将当前节点设置为 rank 0，然后调用：

```text
run_sonic_wpc_torchrun_worker.sh
```

worker 最终使用 `torchrun` 启动：

```text
gear_sonic/train_agent_trl.py
```

### 6.21 正式训练轮数

```bash
++algo.config.num_learning_iterations=30000
```

这是 Hydra 命令行配置覆盖。

`++` 表示字段存在时覆盖，不存在时添加。

该参数明确把 PPO 训练轮数设为 30000。

训练不是按照固定小时数停止，而是在完成 30000 个 iteration 后自然结束。

WPC 配置中的 curriculum 总步数按照：

```text
30000 × 24 = 720000
```

设计，所以正式命令显式使用 30000 轮，而不是基础 PPO 配置中的 100000 轮默认值。

## 7. 正式训练中的 WPC 行为

正式命令没有使用冒烟测试中的以下覆盖：

```text
cap_curriculum_scale_range=[1.0,1.0]
window_no_load_ratio=0.0
```

因此正式训练会使用默认 WPC curriculum：

- 训练初期负载较轻；
- 随训练进度逐渐提高负载；
- 混合无负载、单手负载和双手负载窗口；
- 后期达到完整负载尺度；
- critic 在训练时接收手部载荷 privileged observation。

正式训练不应该从第一轮开始强制所有环境承受最大负载，否则可能破坏渐进学习过程。

## 8. 如何判断训练成功启动

启动后应看到类似信息：

```text
repo=/root/xuxiangling/sonic
branch=feat/wpc-heavy-payload
node_rank=0
nnodes=1
nproc=8
exp=manager/universal_token/all_modes/sonic_Unitree_G1_WUJI_wpc
checkpoint=/root/xuxiangling/sonic/sonic_release/last_wpc.pt
```

随后应看到：

```text
===training policy===
Learning iteration
```

训练日志应逐步出现：

```text
Env/wpc/mean_load_kg
Env/wpc/max_load_kg
Env/wpc/cap_scale
Env/wpc/mean_hand_force_n
loss
reward
fps
ETA
```

训练初期 `cap_scale` 和平均负载可能很小，这是正常 curriculum 行为。

## 9. 从 tmux 安全离开

不要关闭训练，也不要按 `Ctrl+C`。

在 tmux 中依次按：

```text
Ctrl+B
```

松开两个键，然后按：

```text
D
```

这叫 detach，只是离开 tmux 界面，训练仍在服务器中继续。

SSH 连接随后可以安全断开。

## 10. 重新连接后进入训练会话

重新 SSH 登录服务器后，查看会话：

```bash
tmux ls
```

预期看到类似：

```text
sonic_wpc_train: 1 windows
```

重新进入：

```bash
tmux attach -t sonic_wpc_train
```

进入后可以继续看到训练终端输出。

## 11. 训练监控

建议另外打开一个 SSH 终端进行监控，不要在训练终端中反复执行检查命令。

### 11.1 监控 GPU

```bash
watch -n 2 nvidia-smi
```

含义：

- `watch`：重复执行后面的命令；
- `-n 2`：每 2 秒刷新一次；
- `nvidia-smi`：显示 GPU 使用率、显存和进程。

正常情况下，GPU 0 到 7 都应存在对应训练进程并保持显存占用。

按 `Ctrl+C` 只会退出 `watch`，不会停止 tmux 中的训练。

### 11.2 查看 checkpoint

```bash
watch -n 30 \
  "find /root/xuxiangling/sonic/training_checkpoints/sonic_wpc_server_001 \
  -maxdepth 1 -name '*.pt' -printf '%f  %s bytes\n' 2>/dev/null | sort"
```

该命令每 30 秒列出一次实验目录中的 `.pt` 文件。

`-maxdepth 1` 表示只检查实验目录本层。

`-name '*.pt'` 只匹配 checkpoint。

`-printf` 输出文件名和字节大小。

`2>/dev/null` 隐藏目录尚未创建时的错误输出。

`sort` 按名称排序。

### 11.3 查看 checkpoint 目录大小

```bash
du -sh /root/xuxiangling/sonic/training_checkpoints/sonic_wpc_server_001
```

`du -sh` 显示目录总占用，并使用易读单位。

### 11.4 查看磁盘剩余空间

```bash
df -h /root/xuxiangling/sonic
```

训练期间应定期确认磁盘没有接近满载。

## 12. 训练输出

checkpoint 目录：

```text
/root/xuxiangling/sonic/training_checkpoints/sonic_wpc_server_001/
```

主要文件包括：

```text
config.yaml
meta.yaml
last.pt
model_step_002000.pt
model_step_004000.pt
...
model_step_030000.pt
```

`config.yaml` 保存本次训练的完整配置。

`meta.yaml` 保存最大训练步数等元数据。

`last.pt` 默认每 50 轮覆盖一次，代表最近一次周期保存状态。

`model_step_*.pt` 默认每 2000 轮永久保存一份。

30000 轮通常产生 15 个 `model_step_*.pt` 和一个持续覆盖的 `last.pt`。

torchrun 日志目录：

```text
/root/xuxiangling/sonic/sonic_launch/logs/sonic_wpc_server_001/
```

## 13. 如何停止训练

如果确实需要主动停止：

1. 使用 `tmux attach -t sonic_wpc_train` 进入训练会话；
2. 在训练终端中按 `Ctrl+C`；
3. 等待各个 `torchrun` 子进程退出；
4. 使用 `nvidia-smi` 确认 GPU 进程已经消失。

不要直接使用：

```bash
tmux kill-session -t sonic_wpc_train
```

来代替正常停止，因为强行结束会话可能让训练进程来不及清理资源。

`last.pt` 默认每 50 轮保存一次。如果在两次保存之间中断，最新 `last.pt` 可能比终端显示的训练轮数落后最多约 49 轮。

## 14. GPU 数量不同时如何修改

### 14.1 单 GPU

```text
NPROC=1
CUDA_VISIBLE_DEVICES=0
```

### 14.2 两张 GPU

```text
NPROC=2
CUDA_VISIBLE_DEVICES=0,1
```

### 14.3 四张 GPU

```text
NPROC=4
CUDA_VISIBLE_DEVICES=0,1,2,3
```

### 14.4 八张 GPU

```text
NPROC=8
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7
```

`NPROC` 必须与 `CUDA_VISIBLE_DEVICES` 中列出的 GPU 数量一致。

## 15. CUDA OOM 时如何处理

如果出现：

```text
CUDA out of memory
```

先停止当前训练，然后降低：

```text
NUM_ENVS=4096
```

依次尝试：

```text
NUM_ENVS=2048
NUM_ENVS=1024
NUM_ENVS=512
```

每次改变正式训练参数时，都应该修改 `EXP_VAR`，例如：

```text
sonic_wpc_server_001_env2048
```

这样可以避免不同配置的 checkpoint 和日志混在同一个目录。

## 16. 训练结束后

训练自然完成后，不要立刻认定 `last.pt` 是最佳模型。

应评估多个后期 checkpoint，例如：

```text
model_step_020000.pt
model_step_022000.pt
model_step_024000.pt
model_step_026000.pt
model_step_028000.pt
model_step_030000.pt
```

对每个候选模型分别进行：

- 有 WPC 负载评估；
- 无负载对照评估；
- 成功率和进度比较；
- MPJPE、速度和加速度误差比较；
- 必要的渲染检查。

选出表现合适的 `.pt` 后，再使用 WPC ONNX 导出脚本生成部署模型。
